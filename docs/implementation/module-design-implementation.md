## 0. 范围裁定

| 块 | 状态 |
|---|---|
| 模块身份、manifest、解析、错误条件 | 已落地 |
| 语法统一（`using`） | 已落地 |
| **包管理器层**（lockfile、版本仲裁、registry） | 推迟 |

推迟的理由：包管理是**分发**问题，模块是**编译单元划分**问题。两者共用 `dependencies`
这一张表，但不该共用一次落地。

## 1. 为什么分三阶段

不是按「难度」分，是按**耦合**分：身份与 manifest 是地基；语法只有在身份定了之后才好统一；
错误条件要等前两者都定下来才有稳定的形状。先做语法会让错误信息返工两遍。

## 3. 边界（明确不做）

- **lockfile** —— 需要 registry，见上。
- **版本仲裁** —— 同上。
- **registry / 包管理器** —— 分发问题。
- **codegen 标识符前缀** —— 见 [`../design/module-design.md`](../design/module-design.md) 的开放项。
- **约束系统重构** —— 另开。

## 7. 错误条件的收敛原则

**一个条件一句话。** 同一个错误条件在两个编译器里各写一段描述必然漂移；
收敛成一条，两边都读它。

**结构上不可能的错误不写检查。** 有的组合（例如某个修饰符出现在另一个修饰符之后）
在解析层就已经不可能出现，加检查只会让「为什么有这个分支」变成永久疑问。

## 8. import 冲突的两半

import 冲突检查拆成两半，**职责不同，不能合并**：

| 半边 | 回答的问题 | 键 |
|---|---|---|
| `decl_importable` | 这个符号**能不能被看到**（可见性） | 声明 |
| `record_import_binding` | 这个**拼写**归谁 | （目标模块, 原名） |

**身份 =（目标模块, 原名）**，不是本地拼写。`using "m" { A as B }` 里 `B` 是本地拼写，
`A` 才是身份的一部分。

**时机**：绑定要早（收签名前），碰撞检查要晚（要 `nodeSourceInfoMap` 与 scope）。
早了碰撞检查会**静默跳过**。两件事分开跑。

## 9. CLI 错误的信封规则

- 一律 `Error: ` 前缀 + **首词大写**。
- **缺路径**报 `Missing path`，**缺值**报 `Missing value` —— 两个是不同的调用错误。
- 用法（usage）只在**参数解析失败**时打印，业务错误不打印 usage。
- 不得让 `NSCocoaErrorDomain` 这类宿主域泄漏到用户可见文本里。

## 10. 诊断比较是无条件的

**不比较「编译器说了什么」的预言机不是预言机。** 两编译器可以各自绿着套件、
同时对同一段源码给出不同的诊断。

诊断比较现在**无条件开启**，没有开关。曾经的 `--compare-diagnostics` 仍是 inert
兼容参数（`tests/compiler-runner/cli.koral` 仍接受它，只为既有调用不破），
**不必再传，也关不掉**。规则从「必须开着」变成「不存在关掉这个动作」。
