# 设计公理与复杂度预算

> **Status**：Accepted
> **范围**：跨主题的取舍判据——复杂度预算（拒绝清单）与设计公理
> **共同前提**（身份是声明的 `DefId`）见 [`README.md`](README.md)。
> **本文不记任何子系统的具体取舍**——只记「取舍按什么判」。判据被引用，不被复述。

## 摘要

Koral 的取舍判据有两条腿：**复杂度预算**（默认拒绝的类别清单，出口只有一条）与
**设计公理**（冲突时的优先序）。两者从同一个目标派生——**让生成器少走错路、
让审阅者少要看点**（[`../../README.md`](../../README.md)）。

## 背景

语言会长大。每一次「再加一个能力」都在花同一份预算；没有预算时，每个单项提案
都局部合理，合起来把语言推向「必须全局推断才能编译、必须扫调用图才能读」的复杂度——
而那恰好是 Koral 要消除的两件事。

所以把预算写成清单、把优先序写成公理：取舍有处可查，否决有处可引，
新提案有一个说得出名字的闸门。

## 非目标

- **身份前提**（身份是声明的 `DefId`，名字只在解析边界/显示/C 改编合法）→ [`README.md`](README.md)「共同前提」，本文不复述。
- **各子系统为什么这样设计** → 各子系统文档；本文只给判据。
- **工程写法的细则正本**（拼写、排版契约）→ [`../../toolchain/koral-syntax/README.md`](../../toolchain/koral-syntax/README.md)。

## 方案

### 复杂度预算

复杂度是**有限预算**。列入拒绝清单的类别**默认不再受理**；未列入的类别也不免费——
都要过下文「提案过闸」。

预算的**出口只有一条**：提案指明它**替换**哪条现有规则（见公理 7），并且在可读性
或局部可判断上净赚。只有进项没有出项的提案，是纯叠加。

### 拒绝清单（登记在案）

| 类别 | Koral 的主流表达 | 依据 |
|---|---|---|
| 关联类型 | 「关联物」一律写成类型参数：`Iterator[T]`、`Iterable[T, R]` | 投影归一化让 trait 身份无法在声明处定死，与共同前提「身份是 DefId 含实参」冲突 |
| 下标语法 trait | `[]` 是内建规则：只覆盖 `String`、`List`、`Deque`、`Dict`、裸指针；用户类型不可实现、泛型约束不可增加 | `[]` 表达 place（读 / 写 / 嵌套更新）；公开 trait 接不住 place 语义，接得住就得把 lvalue 模型公开 |
| 函数重载 | 模块级一个名字一个属主；类型上的能力靠 receiver 与 trait 身份区分 | 重载集按调用点实参选型，把「名字→身份」从解析边界拖到调用点，破坏局部可判断 |
| 高阶类型 | 泛型是单态化模板，类型参数只代入类型 | 单态化没给类型构造器留实例化语义；求解会退化成全局推断 |
| 双参数错误类型 | `Result[T]` 单参数，错误侧是合成的 `Error` trait object | 双参数引入 `From[E]` 转换格与签名级错误类型推断；`or return` 的统一传播建立在错误侧固定之上 |

**依据列是「现在的理由」**（按公理推出），不是「当年否决时的取舍记录」——
本清单首次登记于本文档，**不追认历史论证**（[`README.md`](README.md)「材料不足就如实记」）。

### 设计公理

冲突时按序号排优先；同号内按「摘要」里的目标权衡。

1. **可读性优于抽象完备性。** 缺抽象手段可以是故意的。声明处可变性让审阅者一眼可判
   「谁能改什么」（[`type-semantics.md`](type-semantics.md)）；`Clone` 明定浅拷贝，不提供
   深拷贝抽象。宁可少一层抽象，不少一处可读。
2. **局部可判断优于全局推断。** 工具在局部就能判：名字解析一次定身份、裸名不是解析、
   prelude 是显式绑定（[`name-resolution.md`](name-resolution.md)）；可变性在声明处；
   `Self` 不出现在方法参数与返回类型，object safety 局部可判。需要全程序求解才能
   判定的规则，不进语言。
3. **显式优于隐式引用转换。** managed-ref 语义整体删除；`&` / `&mutable` 是显式取址，
   `*T` / `*mutable T` 是显式裸指针拼写，`clone` 显式（[`type-semantics.md`](type-semantics.md)）。
   不引入隐式引用转换层级。
4. **库作者复杂换取用户简单。** 用户只有一个 receiver 形态 `self`，可变性差异全部由
   类型声明吸收（[`std-api-design.md`](std-api-design.md)）；消耗 / 观察的细则是 std
   作者的负担，不是用户的。下标 place 规则、链式比较降级、`and then` / `or else` /
   `or return` 由编译器承接。复杂度往作者侧和编译器侧收，不往用户侧摊。
5. **不追求语法 trait 化。** 语法能不能定制，按「是不是值代数」判：算术与比较是值代数，
   走 trait；下标是 place、位运算是内建位语义，都不走公开 trait（`guide`「运算符重载」）。
   语法糖降级为既有机制，不为它新增 trait。
6. **一个问题原则上只提供一种主流表达。** 可变性只有声明处；receiver 只有 `self`；
   错误传播只有 `or return`（无 `throw` / `try` / `catch`，也没有第二种传播运算符）；
   `using` 一种拼写；控制流一种分支形状。例外必须登记在案（[`std-api-design.md`](std-api-design.md)
   的遗留例外即此用途）。
7. **新能力应替换现有规则，而不是叠加新规则。** 提案必须写明替换哪条；写不出的按叠加
   处理，拒绝。已有的替换先例：managed-ref 语义整体删除、weak 改为 `?T`、which-method
   按 DefId 重写方法表（[`../implementation/identity-matching-tracking.md`](../implementation/identity-matching-tracking.md)）。
   文档 / 实现 / 文法不一致时收敛是义务，不是三份并存。
8. **以 koralfmt 规范工程写法。** 工程写法的正本是 formatter（`koralfmt`）的契约
   （[`../../toolchain/koral-syntax/README.md`](../../toolchain/koral-syntax/README.md)），
   被否决的拼写靠 gate 拦截，不靠人工维护第二套规则。设计文档不复述拼写细则。
9. **局部可推理。** 人读一段就能判：错误从表达式里走（无 `throw` / `try`，不用扫调用图）、
   求值顺序全规定、`when` 穷尽性编译器审（[`../../README.md`](../../README.md)「Why Koral
   is shaped this way」）。与公理 2 的分工：**2 给工具**（局部可判），**9 给读者**（局部可推）。

### 提案过闸

新能力提案按顺序回答，答不出来的不进设计：

1. **落在拒绝清单里吗？** 在——默认拒绝；要解禁整个类别，先来改这份清单。
2. **替换哪条现有规则？** 写不出 → 纯叠加 → 拒绝（公理 7）。
3. **读法收益在哪？** 说清是哪位读者（生成器 / 审阅者 / 库作者）在哪一处变简单了（公理 1、4、9）。
4. **局部可判断 / 可推理是否保持？** 需要全局推断或扫调用图才能判的，回炉（公理 2、9）。

## 替代方案

- **放进 [`README.md`](README.md)「共同前提」**——否掉。前提是技术事实，公理是取舍判据，
  混在一处会让 README 同时承担地图与宪法；且拒绝清单需要 Status 与演进位。
- **放进 [`../implementation/developer-guide.md`](../implementation/developer-guide.md)**——否掉。
  那份是「怎么参与实现」的章程，读者是贡献者；公理的读者是评审取舍的人。公理被实现
  记录引用，不是实现规程的一部分。
- **每条公理各写进对应子系统文档**——否掉。违反「一条事实只有一个家」，且公理的价值
  恰在跨主题一致。

## 风险与未决

- **拒绝清单会僵化。** 出口是「替换式提案」+ 来本文档改清单；将来某类别确需解禁时在
  `## 演进` 记录，不静默破例。
- **公理排序未量化。** 同号冲突目前靠讨论，暂不引入打分表。
- **「工程写法」的边界未划定。** 当前只覆盖 formatter 契约内的拼写与排版；命名与注释
  文风是否纳入，未决。
